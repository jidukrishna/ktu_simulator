1. Model-View-Controller (MVC) Pattern 🔥 High Priority

▾

When building a web application, developers need a structured approach so the code doesn't turn into a tangled mess. This structure is called software architecture, and the most widely used architecture in modern web development is MVC.

🟡 DEFINITION

MVC (Model–View–Controller) is a software design pattern that divides an application into three interconnected components so that internal representations of information are separated from how information is presented to the user.

The Three Components

  • Model — Manages the application's data and business logic. Handles CRUD (Create, Read, Update, Delete) operations, stores/retrieves data, and sends it to the Controller. Mainly used by backend developers and DB analysts.
  • View — Handles the presentation layer (the UI the user actually sees). Built with HTML/CSS/JS/React/Angular.
  • Controller — The middleman between Model and View. Processes user input and updates the Model or View as needed.
MVC Data Flow

→
View (UI)
→
Controller
→
Model
→
Database
Data returns the same path in reverse: Database → Model → Controller → View → User

Step-by-Step Workflow

  1. User interacts with the View (UI).
  2. Controller receives user input and interprets it.
  3. Controller sends instructions to the Model.
  4. Model fetches or updates data in the Database.
  5. Model returns the data to the Controller.
  6. Controller passes data to the View.
  7. View displays the data to the User.
🟢 EXAMPLE SCENARIO

A client requests www.productlist.com. The request goes to the Controller, which asks the Model for data. The Model fetches raw data from the database (e.g. product: Laptop, price: 2000). The Controller sends this to the View, which renders it using HTML/CSS into a styled page the user sees.

Advantages of MVC

  • Scalable — easy to expand and maintain.
  • Organized — separates the app into Model, View, Controller.
  • Collaborative — frontend and backend developers can work independently.
  • Reusability — components can be reused across projects.
🔵 NOTE

Popular real-world frameworks/stacks following MVC: MERN (MongoDB, Express, React, Node.js), MEAN, and Laravel.

🔴 COMMON MISTAKE

Students often confuse the direction of data flow — remember, the View never talks directly to the Model. The Controller is always the middleman.

2. Presentational & Container Components Pattern

▾

This pattern separates the application layer (logic) from the view layer (UI) in a React app. It's one of the earliest and most fundamental React architecture patterns.

🟡 DEFINITION

Presentational components focus on how things look — pure UI, styling, and markup. Container components focus on how things work — data fetching, state, and business logic — and pass data down to presentational components via props.

Presentational Components
  • Receive data only via props
  • Usually stateless / function components
  • Don't know where data comes from
  • Contain only HTML/JSX and styling
Container Components
  • Fetch data / connect to state management
  • Pass data down via props
  • Often class components or hooks-based
  • No DOM markup of their own
Presentational Component
// presentational component
const Users = props =>
  (<ul>
    {props.users.map(user =>
      (<li>{user.name}</li>))
    }
  </ul>)

Explanation: Users takes a users array via props and just renders it as a list — it has zero idea where that data came from.

Container Component
// container component
class UsersContainer extends React.Component {
  constructor() {
    super();
    this.state = { users: [] };
  }
  componentDidMount() {
    axios.get('/users').then(res => this.setState({ users: res.data }));
  }
  render() {
    return <Users users={this.state.users} />;
  }
}

Explanation: UsersContainer fetches data from an API in componentDidMount(), stores it in state, and passes it down to the "dumb" Users presentational component.

🔵 NOTE

This pattern is largely superseded today by Hooks + Custom Hooks, which let you extract the "container" logic without a wrapper component — but it still appears in exams and legacy codebases.

MCQ
Q. Which type of component is typically stateless and only contains HTML/JSX and styling?
  • Presentational Component
  • Container Component
  • Higher-Order Component
  • Custom Hook
✅ Answer: Presentational Component. It focuses purely on UI/look, receiving data via props.

3. Higher-Order Components (HOC) Pattern 🔥 High Priority

▾
🟡 DEFINITION

A Higher-Order Component is a function that takes an existing component as input and returns a new component with extra features — a technique for reusing component logic without duplicating code.

🟢 REAL-WORLD ANALOGY

Think of a coffee shop: you have plain coffee (the original component). You pass it through a "flavor machine" (the HOC). The machine adds vanilla or caramel (extra features) and gives you back a new, enhanced coffee (the enhanced component).

Why use HOCs?

  • Reuse logic across multiple components (e.g. authentication checks, logging, data fetching) without copy-pasting.
  • Keep components focused on a single responsibility.
🔴 COMMON MISTAKE

An HOC does not modify the input component — it wraps it and returns a brand-new component. Mutating the original component breaks the pattern's composability.

4. Custom Hooks Pattern 🔥 High Priority

▾
🟢 IMAGINE BUILDING WITH LEGO

Components = LEGO blocks (used to build a house, car, robot). Hooks = special tools that help you build smarter. Custom Hooks = tools you make yourself to solve a recurring problem — e.g. a useCounter hook that any LEGO door can attach to, instead of rebuilding counting logic every time.

🟡 DEFINITION

A Custom Hook is a JavaScript function whose name starts with use and that can call other hooks. It lets you extract component logic into a reusable function.

Where Custom Hooks Sit in a Component

→ calls →
useFetch(url)

How Custom Hooks fit into React Architecture

UI Layer (Components)
  • Focused on rendering UI
  • Uses props & state
  • Stays "dumb" — just takes data and displays it
Logic Layer (Custom Hooks)
  • Encapsulates stateful / side-effect logic
  • Handles fetching, subscriptions, timers, auth, forms
  • Reusable logic pluggable into any component
Custom Hook: useFetch
import { useState, useEffect } from "react";

// Custom Hook
function useFetch(url) {
  const [data, setData] = useState(null);
  const [loading, setLoading] = useState(true);

  useEffect(() => {
    fetch(url)
      .then(res => res.json())
      .then(data => {
        setData(data);
        setLoading(false);
      });
  }, [url]);

  return { data, loading };
}
Using the Custom Hook
function Users() {
  const { data: users, loading } =
    useFetch("https://jsonplaceholder.typicode.com/users");

  if (loading) return <p>Loading...</p>;
  return (
    <ul>
      {users.map(user => (
        <li key={user.id}>{user.name}</li>
      ))}
    </ul>
  );
}
export default Users;

Explanation: useFetch encapsulates the fetch-and-loading logic. Any component can now reuse it just by calling useFetch(url) — no copy-pasted useEffect blocks.

🔵 NOTE — Organization

House (Component) → uses Door (Component) → uses useCounter (Custom Hook). Components = what you see. Custom Hooks = your own reusable recipes.

MCQ
Q. What naming convention must a Custom Hook follow in React?
  • It must end in "Hook"
  • Its name must start with "use"
  • It must be a class
  • No convention required
✅ Answer: name must start with "use". This lets React's linter and other hooks recognize it correctly, e.g. useFetch, useCounter.

5. Context API Pattern 🔥 High Priority

▾

The Context API lets you share data across the component tree without manually passing props at every level — a problem known as "prop drilling". It's ideal for global data like auth status, theme, or language.

🟡 DEFINITION — Prop Drilling

Prop drilling occurs when data must be passed through multiple layers of components before reaching the component that actually needs it — even though the intermediate components don't use that data themselves. This slows development and makes the app harder to maintain.

Working (Provider & Consumer)

  • Create context with React.createContext().
  • Provider — acts as parent, passes state down to children.
  • Consumer (or the useContext hook) — uses the state that was passed.

Steps to Implement

  1. Create a React app: npx create-react-app context-api-demo
  2. cd context-api-demo
  3. Create Context.js (defines the context) and WelcomePage.js (consumes it).
Context.js
import React, { createContext } from 'react';
export const UserContext = createContext();

const UserProvider = ({ children }) => {
  const user = { name: 'John Doe', id: 1 };
  return (
    <UserContext.Provider value={user}>
      {children}
    </UserContext.Provider>
  );
};
export default UserProvider;
WelcomePage.js
import React, { useContext } from 'react';
import { UserContext } from './Context';

const WelcomePage = () => {
  const user = useContext(UserContext);
  return (
    <div>
      <h1>Welcome User:</h1>
      <p>Name: {user.name} id: {user.id}</p>
    </div>
  );
};
export default WelcomePage;
index.js — wrap App with Provider
import ReactDOM from 'react-dom';
import UserProvider from './Context';
import App from './App';

ReactDOM.render(
  <UserProvider>
    <React.StrictMode>
      <App />
    </React.StrictMode>
  </UserProvider>,
  document.getElementById('root')
);
🔴 COMMON MISTAKE

If you forget to wrap your component tree in the <Provider>, or pass no value, consuming components will render blank / receive undefined.

✅ Answer: Prop drilling. Context lets global data reach deeply nested components directly.

6. React Basics: Components, Props, State, JSX 🔥 High Priority

▾

ReactJS is a component-based JavaScript library used to build dynamic, interactive user interfaces — created by Facebook engineer Jordan Walke. It simplifies building single-page applications (SPAs) with a focus on performance and maintainability.

How does React work? (Virtual DOM)

React creates an in-memory Virtual DOM rather than directly manipulating the browser's real DOM. It performs changes on this virtual copy first, then applies only the minimal necessary updates to the real DOM.

Virtual DOM Update Cycle
State Changes
→

Only changed parts patched to Real DOM
🟡 DEFINITION — Reconciliation

Reconciliation is the process where React compares the new Virtual DOM with the previous one, finds the smallest set of changes, and applies only those to the real browser DOM — this is what makes React fast.

1. Components

A component is a small, reusable, independent piece of UI (a button, form, or entire page) built as a JavaScript function or class. Components accept inputs (props) and return elements describing what should appear on screen.

🔴 COMMON MISTAKE

A component's name MUST start with an uppercase letter (e.g. Car, not car) — otherwise React treats it as a plain HTML tag.

"Hello, World!" in React
import React from 'react';

function App() {
  return (
    <div>
      <h1>Hello, World!</h1>
    </div>
  );
}
export default App;

Line-by-line: import React brings in the library needed to create components/JSX. function App() defines a functional component. return(...) returns JSX describing the UI. export default App makes it usable elsewhere.

Props (Properties)

🟡 DEFINITION

Props are read-only inputs passed from a parent component to a child component — like function arguments in JS or attributes in HTML. Props are immutable (a child cannot change its own props) and enable communication between components.

function Car(props) {
  return <h2>I am a {props.color} Car!</h2>;
}
root.render(<Car color="red" />);

Explanation: color="red" is passed as an attribute; inside the component it's accessible as props.color.

State

🟡 DEFINITION

State is dynamic, mutable data owned by a component. Unlike props, a component can change its own state. When state changes, the component automatically re-renders.

import { useState } from "react";

function Counter() {
  const [count, setCount] = useState(0);
  return (
    <>
      <p>You clicked {count} times</p>
      <button onClick={() => setCount(count + 1)}>Click me</button>
    </>
  );
}

Explanation: useState(0) returns an array: the current value (count) and a setter function (setCount). Calling setCount updates state and triggers a re-render.

JSX (JavaScript XML)

🟡 DEFINITION

JSX lets you write HTML-like syntax directly inside JavaScript. JSX converts HTML tags into React elements without needing manual createElement() / appendChild() calls.

useEffect() — Initialization, Cleanup, Side-Effects

useEffect(() => { // effect code return () => { // cleanup code (optional) }; }, [dependencies]);
🔵 NOTE — Dependency Array

[] → runs once after first render. [dep] → runs whenever dep changes. No array at all → runs after every render.

Example: Fetch data when route param changes
import { useParams } from 'react-router-dom';
import { useState, useEffect } from 'react';

function UserProfile() {
  const { id } = useParams();
  const [user, setUser] = useState(null);

  useEffect(() => {
    fetch(`https://api.example.com/users/${id}`)
      .then(res => res.json())
      .then(data => setUser(data));
  }, [id]);

  if (!user) return <p>Loading...</p>;
  return <h1>{user.name}</h1>;
}

Explanation: useParams() (from React Router) reads the dynamic :id segment from the URL. useEffect re-fetches the user whenever id changes, and the component shows a loading state until data arrives.

🔴 COMMON MISTAKE

Forgetting the dependency array (or listing the wrong dependencies) causes infinite re-render loops or stale data bugs — a very common exam trick question.

1. Mounting — creating & inserting into the DOM

  1. constructor() — initializes state, binds methods. Runs before mounting.
  2. getDerivedStateFromProps(props, state) — updates state based on props. Runs before every render.
  3. render() — renders JSX and updates the DOM.
  4. componentDidMount() — invoked right after the component is mounted (once, after first render). Great place for API calls.
constructor() — sets up initial state
class Header extends React.Component {
  constructor(props) {
    super(props);           // must call super(props) first — inherits from React.Component
    this.state = { favoritecolor: "red" };
  }
  render() {
    return <h1>My Favorite Color is {this.state.favoritecolor}</h1>;
  }
}
const root = ReactDOM.createRoot(document.getElementById('root'));
root.render(<Header />);

Explanation: constructor() is called before anything else, when the component is initiated — the natural place to set up initial state. Always call super(props) first; it initiates the parent's constructor and lets the component inherit methods from React.Component.

render() — outputs the HTML
class Header extends React.Component {
  render() {
    return (
      <h1>This is the content of the Header component</h1>
    );
  }
}

Explanation: render() is the only required method in a class component — it actually outputs HTML to the DOM.

componentDidMount() — runs after first render
class Header extends React.Component {
  constructor(props) {
    super(props);
    this.state = { favoritecolor: "red" };
  }
  componentDidMount() {
    setTimeout(() => {
      this.setState({ favoritecolor: "yellow" });
    }, 1000);
  }
  render() {
    return <h1>My Favorite Color is {this.state.favoritecolor}</h1>;
  }
}

Explanation: componentDidMount() runs once the component is already placed in the DOM — the correct place for statements that require the component to exist on the page (like starting a timer or an API call). Here, one second after mounting (color starts as "red"), the timer fires and updates state to "yellow", which triggers a re-render (the Updating phase).

2. Updating — re-rendering due to state/prop changes

A component updates whenever its state or props change. React calls five built-in methods, in this order, when updating — only render() is required; the rest are optional:

  1. getDerivedStateFromProps()
  2. shouldComponentUpdate()
  3. render()
  4. getSnapshotBeforeUpdate()
  5. componentDidUpdate()
shouldComponentUpdate() — controls whether React re-renders
class Header extends React.Component {
  constructor(props) {
    super(props);
    this.state = { favoritecolor: "red" };
  }
  shouldComponentUpdate() {
    return false; // tells React to SKIP re-rendering
  }
  changeColor = () => {
    this.setState({ favoritecolor: "blue" });
  }
  render() {
    return (
      <div>
        <h1>My Favorite Color is {this.state.favoritecolor}</h1>
        <button type="button" onClick={this.changeColor}>Change color</button>
      </div>
    );
  }
}

Explanation: shouldComponentUpdate() lets you return a boolean deciding whether React should continue rendering. The default is true. Here it always returns false, so clicking the button updates state internally but the UI never visually re-renders — a common performance-tuning (and exam trick) method.

componentDidUpdate() — runs after an update completes
class Header extends React.Component {
  constructor(props) {
    super(props);
    this.state = { favoritecolor: "red" };
  }
  componentDidMount() {
    setTimeout(() => {
      this.setState({ favoritecolor: "yellow" });
    }, 1000);
  }
  componentDidUpdate() {
    document.getElementById("mydiv").innerHTML =
      "The updated favorite is " + this.state.favoritecolor;
  }
  render() {
    return (
      <div>
        <h1>My Favorite Color is {this.state.favoritecolor}</h1>
        <div id="mydiv"></div>
      </div>
    );
  }
}

Explanation: On mount, the color renders as "red". After 1 second, componentDidMount's timer changes it to "yellow" — this state change triggers an update, and componentDidUpdate() then runs, updating a separate DOM element to reflect the new value.

3. Unmounting — removal from the DOM

React has only one built-in method for this phase:

componentWillUnmount() — cleanup before removal
componentWillUnmount() {
  // e.g. clear timers, cancel subscriptions, remove event listeners
  clearInterval(this.timerID);
}

Explanation: componentWillUnmount() is called right when the component is about to be removed from the DOM — the final lifecycle phase, and the correct place to clean up timers, subscriptions, and listeners to avoid memory leaks.

🟡 DEFINITION

componentDidMount() = "I've just appeared." componentDidUpdate() = "Something about me changed." componentWillUnmount() = "I'm about to disappear — clean up after me."

🔵 NOTE — Hooks Equivalent

In functional components, useEffect(() => {...}, []) ≈ componentDidMount; useEffect(() => {...}, [dep]) ≈ componentDidUpdate; the cleanup function returned from useEffect ≈ componentWillUnmount.

6. The Event Loop 🔥 High Priority

▾
🟡 DEFINITION

The Event Loop is the mechanism that allows Node.js to handle asynchronous tasks efficiently without blocking execution, even though Node.js runs on a single thread. It executes synchronous JS first, then processes async operations, delegating heavy I/O tasks to the libuv library.

Why is it Important?

  • Allows non-blocking execution despite being single-threaded.
  • Handles I/O-bound tasks efficiently.
  • Makes Node.js suitable for scalable applications like web servers.
Classic Event Loop Example
console.log("This is the first statement");

setTimeout(function() {
  console.log("This is the second statement");
}, 1000);

console.log("This is the third statement");

// Output order:
// This is the first statement
// This is the third statement
// (after 1000ms) This is the second statement

Explanation: Synchronous statements 1 and 3 run immediately. setTimeout is delegated and its callback only runs after the timer expires and the call stack is empty.

Node.js Request Handling Architecture
Client Requests
→
Event Queue
→
Event Loop
simple/non-blocking task → executed immediately  |  I/O/blocking task ↓
Thread Pool (libuv, default 4 threads)
→
Operation Completed
→
back to Event Queue → callback executed → Response to Client

Phases of the Event Loop

#PhaseWhat it Does
1TimersExecutes callbacks scheduled by setTimeout() / setInterval()
2Pending CallbacksExecutes I/O callbacks deferred from the previous loop cycle
3Idle, PrepareInternal use only
4Poll (main phase)Executes most tasks — I/O, file reading, HTTP requests
5CheckProcesses setImmediate() callbacks
6Close CallbacksExecutes callbacks for closed sockets/streams/emitters
🔵 NOTE — Highest Priority

process.nextTick() and resolved Promise callbacks have the highest priority — they run after every phase, before the loop moves to the next phase. process.nextTick() always runs before Promise callbacks.

Exam trap: students often think setTimeout(fn, 0) runs "immediately". It actually still waits for the current call stack and microtask queue (nextTick/Promises) to clear first.

How Server-Side Rendering Actually Works

  1. Request from Client — the browser sends an HTTP request to the server.
  2. Server Fetches Data — the server (e.g. Node.js/Express, Django, Flask) queries a database or other data source for the required data.
  3. Template Engine Renders HTML — the server passes that data to a template engine (EJS, Handlebars, Pug, Jinja2, etc.), which merges the HTML template (with placeholders/variables) and the server-side data into one complete HTML page.

12. User Authentication: Sessions vs JWT 🔥 High Priority

▾

Sessions and JSON Web Tokens (JWT) are two methods for a website to remember a logged-in user across multiple requests, since the underlying HTTP protocol is stateless (it "forgets" who you are after every interaction). The key difference is where the user's data is stored.

Sessions (Stateful Authentication)

🟡 DEFINITION

With session-based authentication, the server creates and stores a record of the logged-in user.

Session-Based Authentication Flow
1. Login (credentials)
→
2. Server creates Session + stores it server-side
→
3. Server sends Session ID as a cookie
→
4. Browser auto-sends cookie on every request
→
5. Server looks up session by ID
  1. Log in: User submits credentials; server validates them.
  2. Create session: Server generates a unique Session ID and stores it with the user's info (user ID, access level).
  3. Send cookie: Server sends the Session ID to the browser as a cookie.
  4. Subsequent requests: Browser automatically sends the cookie back; server looks up the session data using the Session ID to verify identity.

JWT (Stateless Authentication)

🟡 DEFINITION

A JSON Web Token (JWT) is a secure way to send information between client and server — JSON data secured with a cryptographic signature (via HMAC, or asymmetric methods like RSA/ECDSA).

  1. Log in: User sends credentials.
  2. Generate token: Server verifies credentials, creates a JWT containing a JSON payload (user ID, expiration, claims), digitally signed with a secret key.
  3. Return token: Server sends the JWT to the client.
  4. Subsequent requests: Client sends the JWT in the Authorization: Bearer <token> header.
  5. Verify token: Server verifies the signature using its secret/public key — no database lookup needed.
JWT Authorization Flow
1. Login (credentials)
→
2. Server generates & sends JWT
→
3. Client stores & sends JWT in Authorization header
→
4. Server verifies signature
→
5. Access granted / denied
🔵 NOTE — JWT Structure

A JWT string has 3 parts separated by dots: Header.Payload.Signature — e.g. xxxxx.yyyyy.zzzzz. The Header specifies the algorithm; the Payload holds claims (user ID, expiry); the Signature verifies the token hasn't been tampered with.

🔎 Deep Dive: Structure of a JWT

1. Header — metadata about the token
{
  "alg": "HS256",
  "typ": "JWT"
}

alg: the algorithm used for signing (e.g. HS256, RS256). typ: the token type, always "JWT". This gets Base64Url encoded, e.g. eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.

2. Payload — the claims (data about the user)
{
  "userId": 123,
  "role": "admin",
  "exp": 1672531199
}
Common ClaimMeaning
iss (Issuer)Identifies who issued the token
sub (Subject)Represents the user or entity the token is about
aud (Audience)Specifies the intended recipient
exp (Expiration)Defines when the token expires
iat (Issued At)Timestamp when the token was created
nbf (Not Before)Specifies when the token becomes valid
3. Signature — ensures token integrity
HMACSHA256( base64UrlEncode(header) + "." + base64UrlEncode(payload), secret )

Explanation: The signature is generated from the encoded header + payload combined with a secret key, using the algorithm named in the header (HS256 here). If anyone tampers with the header or payload, re-computing this signature on the server will no longer match — proving the token was altered.

4. Final JWT — Header.Payload.Signature joined by dots
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJ1c2VySWQiOjEyMywicm9sZSI6ImFkbWluIiwiZXhwIjoxNjcyNTMxMTk5fQ.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c

This is what actually gets sent in the Authorization: Bearer <token> header on every authenticated request.

Passport.js — Authentication Middleware

🟡 DEFINITION

Passport.js is authentication middleware for Node.js. It's extremely flexible and modular via "strategies" — small plug-in modules for each authentication method (local username/password, JWT, Google OAuth, Facebook, etc.), letting you add authentication to any Express app without rewriting core logic.

Passport Local Strategy — Setup
npm install passport passport-local express-session
const passport = require('passport');
const LocalStrategy = require('passport-local').Strategy;
const session = require('express-session');

app.use(session({ secret: 'mySecretKey', resave: false, saveUninitialized: false }));
app.use(passport.initialize());
app.use(passport.session());

// Define the local strategy
passport.use(new LocalStrategy((username, password, done) => {
  // Look up user in DB (pseudo-code)
  findUser(username, (err, user) => {
    if (err) return done(err);
    if (!user || user.password !== password) {
      return done(null, false, { message: 'Incorrect credentials.' });
    }
    return done(null, user);
  });
}));

// Store user id in session
passport.serializeUser((user, done) => done(null, user.id));
// Retrieve user from id stored in session
passport.deserializeUser((id, done) => {
  findUserById(id, (err, user) => done(err, user));
});
Login Route using Passport
app.post('/login',
  passport.authenticate('local', { failureRedirect: '/login' }),
  (req, res) => {
    res.redirect('/dashboard'); // Successful authentication
  }
);

Explanation: passport.authenticate('local', ...) runs the strategy defined above. On success it calls next() into the route handler; on failure it redirects to /login.

Building a Simple Auth System (Login/Signup)

Signup Route — hashing password with bcrypt
const bcrypt = require('bcrypt');

app.post('/signup', async (req, res) => {
  const { username, password } = req.body;
  const hashedPassword = await bcrypt.hash(password, 10); // 10 = salt rounds
  // Save { username, hashedPassword } to database (pseudo-code)
  saveUser({ username, password: hashedPassword });
  res.send('Signup successful!');
});
Login Route — verify password + issue JWT
const jwt = require('jsonwebtoken');
const bcrypt = require('bcrypt');

app.post('/login', async (req, res) => {
  const { username, password } = req.body;
  const user = await findUser(username); // pseudo-code lookup

  if (!user) return res.status(400).send('User not found');

  const isMatch = await bcrypt.compare(password, user.password);
  if (!isMatch) return res.status(401).send('Invalid credentials');

  const token = jwt.sign({ id: user.id, username: user.username }, 'secretKey', { expiresIn: '1h' });
  res.json({ message: 'Login successful', token });
});
Protected Route — verifying the JWT
function verifyToken(req, res, next) {
  const authHeader = req.headers['authorization'];
  const token = authHeader && authHeader.split(' ')[1]; // "Bearer <token>"
  if (!token) return res.status(401).send('No token provided');

  jwt.verify(token, 'secretKey', (err, decoded) => {
    if (err) return res.status(403).send('Invalid token');
    req.user = decoded;
    next();
  });
}

app.get('/dashboard', verifyToken, (req, res) => {
  res.send(`Welcome ${req.user.username}!`);
});

Explanation: bcrypt.hash() never stores plain-text passwords. jwt.sign() issues a signed token on successful login. verifyToken is custom middleware that checks the Authorization header before allowing access to protected routes.

🔴 COMMON MISTAKE

Never store plain-text passwords in the database, and never hardcode the JWT secret key directly in source code for production — use environment variables (.env + dotenv package).

WebSockets

🟡 DEFINITION

WebSocket is a protocol providing a persistent, full-duplex connection between client and server over a single TCP connection — unlike HTTP's request→response model, WebSocket allows continuous, bidirectional communication. Used in chat apps, live notifications, stock tickers, and multiplayer games.

How WebSocket Works

  1. Handshake: Client sends an HTTP request asking to "upgrade" to WebSocket. Server responds with HTTP status 101 Switching Protocols.
  2. Persistent Connection: Once established, the connection stays open for continuous data exchange.
  3. Full-Duplex Communication: Both sides can send and receive data simultaneously.
  4. Data Frames: Data is sent as frames (text, binary, or control frames) for efficient transfer.

GraphQL

🟡 DEFINITION

GraphQL is a query language for APIs (developed by Facebook) and a server-side runtime for executing queries. It's an alternative to REST that lets clients request exactly the data they need — no more, no less — through a single endpoint.

🟢 EXAMPLE — REST vs GraphQL

To get a blog post AND its author's info via REST, you typically need two separate requests (one for the post, one for the author). In GraphQL, you request both in one single query, reducing network overhead.

  user(id: 1) {
    name
    posts {
      title
    }
  }
}

GraphQL Schema Example
type Book {
  id: ID!
  title: String!
  author: String!
  publishedYear: Int
}

type Query {
  getBooks: [Book!]!
  getBookById(id: ID!): Book
}

type Mutation {
  addBook(title: String!, author: String!, publishedYear: Int): Book
  deleteBook(id: ID!): String
}

Explanation: Book defines the data shape. Query defines read operations (like GET in REST). Mutation defines write operations (like POST/PUT/DELETE in REST). ! means the field is non-nullable (required).
